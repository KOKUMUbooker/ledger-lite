# LedgerLite Models

Reference for every model in the app, grouped by build stage.

- **Stage 1**. It is the ledger core.
- **Stage 2 and 3** are planned designs. Treat them as a starting point, since building Stage 1 will teach you things that change them.

## Guiding rules

1. **The ledger stores the money. Business tables store business facts.** A loan's outstanding balance or a savings balance is never a column. It is derived from journal lines.
2. **Ledger tables are append-only.** Posted entries and lines are never updated or deleted. Corrections are made with reversals.
3. **Business tables point at the ledger, never the reverse.** `Loan` knows its journal entry. `JournalEntry` does not know about loans (it only carries a free-text `Reference`).
4. **Terms are copied, not referenced.** When a loan is created, the interest rate, term and method are copied from the product, so later product edits do not change existing loans.
5. **Money is `decimal(18,2)`. Rates are `decimal(9,6)`. Dates that mean "the day it belongs to" are `DateOnly`. Timestamps are UTC `DateTime`.**
6. **Enums are stored as strings** so the database is readable by hand.

## Account

One row in the chart of accounts. A bucket that tracks one kind of value.

| Field           | Type        | Constraints             | Notes                                          |
| --------------- | ----------- | ----------------------- | ---------------------------------------------- |
| Id              | int         | PK                      |                                                |
| Code            | string(20)  | Required, **unique**    | e.g. "1000"                                    |
| Name            | string(200) | Required                | e.g. "Cash"                                    |
| Type            | AccountType | Required                | Stored as string                               |
| ParentAccountId | int?        | FK to Account, Restrict | Hierarchy: control account over sub-accounts   |
| IsActive        | bool        | Default true            | Closed accounts are deactivated, never deleted |

**Rules**

- An account with posted lines cannot be deleted. Deactivate it.
- A parent with children cannot be deleted.
- No balance column. Balance comes from `Account.BalanceFrom(totalDebits, totalCredits)`.
- Postings to inactive accounts are rejected (checked in the Application layer).

## JournalEntry

One financial event. The header of a posting.

| Field             | Type         | Constraints                                             | Notes                                         |
| ----------------- | ------------ | ------------------------------------------------------- | --------------------------------------------- |
| Id                | int          | PK                                                      |                                               |
| Date              | DateOnly     | Required, indexed                                       | Accounting date: the day the event belongs to |
| PostedAt          | DateTime     | Required, UTC                                           | When it was recorded                          |
| Description       | string(500)  | Required                                                | Human-readable                                |
| Reference         | string(100)  | Required (may be empty string)                          | External ref: deposit number, loan number     |
| Source            | EntrySource  | Required                                                | Default Manual                                |
| IdempotencyKey    | string(200)? | **Unique** where not null                               | Stops a retried job posting twice             |
| ReversalOfEntryId | int?         | FK to JournalEntry, Restrict, **unique** where not null | Set only on reversal entries                  |

**Rules (enforced by `JournalEntry.Create`)**

- At least two lines.
- Total debits equal total credits.
- Reversals can only be created through `CreateReversal`.
- Immutable once saved. There are no edit methods.
- An entry can be reversed at most once (unique index).

## JournalLine

One account touched by one event, on the debit or credit side.

| Field          | Type          | Constraints                      | Notes |
| -------------- | ------------- | -------------------------------- | ----- |
| Id             | int           | PK                               |       |
| JournalEntryId | int           | FK to JournalEntry, Restrict     |       |
| AccountId      | int           | FK to Account, Restrict, indexed |       |
| Debit          | decimal(18,2) | >= 0                             |       |
| Credit         | decimal(18,2) | >= 0                             |       |

**Rules**

- Check constraint: `Debit >= 0 AND Credit >= 0 AND (Debit = 0 OR Credit = 0) AND (Debit + Credit) > 0`.
- At most 2 decimal places (domain check).
- Created with `ForDebit(accountId, amount)` or `ForCredit(accountId, amount)`.

# Stage 2: Savings, loans and suspense (planned)

## Entity relationship overview

```
Customer ──< SavingsAccount ──► Account (own liability account)
   │
   └──< Loan >── LoanProduct
         │  │
         │  ├──< LoanInstallment

```

## Customer

A placeholder member record. Kept deliberately small.

| Field        | Type        | Constraints      | Notes |
| ------------ | ----------- | ---------------- | ----- |
| Id           | int         | PK               |       |
| MemberNumber | string(30)  | Required, unique |       |
| FullName     | string(200) | Required         |       |
| Phone        | string(30)? |                  |       |
| CreatedAt    | DateTime    | UTC              |       |
| IsActive     | bool        | Default true     |       |

No link to the ledger. A customer's money lives in their savings and loan accounts.

## SavingsAccount

A member's savings product. Its money lives in its own liability `Account`.

| Field              | Type                 | Constraints                         | Notes                                               |
| ------------------ | -------------------- | ----------------------------------- | --------------------------------------------------- |
| Id                 | int                  | PK                                  |                                                     |
| AccountNumber      | string(30)           | Required, unique                    |                                                     |
| CustomerId         | int                  | FK to Customer, Restrict            |                                                     |
| LedgerAccountId    | int                  | FK to Account, Restrict, **unique** | Own liability account, child of "Customer Deposits" |
| AnnualInterestRate | decimal(9,6)         | >= 0                                | e.g. 0.050000 for 5%                                |
| OpenedOn           | DateOnly             |                                     |                                                     |
| Status             | SavingsAccountStatus |                                     |                                                     |

**Rules**

- Balance is the balance of `LedgerAccountId`. There is no balance column.
- Opening a savings account creates the ledger `Account` in the same transaction.
- The `LedgerAccountId` account's parent is the "Customer Deposits" control account, so the trial balance rolls up through the hierarchy.

## LoanProduct

| ------------------ | -------------- | ---------------- | ----------------------- |
| Id                 | int            | PK               |                         |
| Name               | string(100)    | Required, unique |                         |
| AnnualInterestRate | decimal(9,6)   | >= 0             |                         |
| TermMonths         | int            | > 0              |                         |
| Method             | InterestMethod |                  | Flat or ReducingBalance |
| IsActive           | bool           | Default true     |                         |

## Loan

One loan to one customer.

| Field               | Type           | Constraints                     | Notes                                         |
| ------------------- | -------------- | ------------------------------- | --------------------------------------------- |
| Id                  | int            | PK                              |                                               |
| LoanNumber          | string(30)     | Required, unique                | Used as the journal `Reference`               |
| CustomerId          | int            | FK to Customer, Restrict        |                                               |
| LoanProductId       | int            | FK to LoanProduct, Restrict     | Which template it came from                   |
| Principal           | decimal(18,2)  | > 0                             |                                               |
| AnnualInterestRate  | decimal(9,6)   |                                 | **Copied** from product                       |
| TermMonths          | int            |                                 | **Copied** from product                       |
| Method              | InterestMethod |                                 | **Copied** from product                       |
| ReceivableAccountId | int            | FK to Account, Restrict, unique | Own asset account, child of "Loan Receivable" |
| DisbursedOn         | DateOnly?      |                                 | Null while Pending                            |
| DisbursementEntryId | int?           | FK to JournalEntry, Restrict    | Null while Pending                            |
| Status              | LoanStatus     |                                 |                                               |

**Rules**

- Outstanding principal is the balance of `ReceivableAccountId`. There is no balance column.
- Disbursement posts: debit the loan's receivable account, credit Cash (or the member's savings ledger account).
- The loan is Closed when its receivable balance reaches zero.

## LoanInstallment

The expected repayment schedule, generated at disbursement. It never changes after generation.

| Field        | Type          | Constraints          | Notes        |
| ------------ | ------------- | -------------------- | ------------ |
| Id           | int           | PK                   |              |
| LoanId       | int           | FK to Loan, Restrict |              |
| Number       | int           | Unique per loan      | 1, 2, 3, ... |
| DueDate      | DateOnly      |                      |              |
| PrincipalDue | decimal(18,2) | >= 0                 |              |
| InterestDue  | decimal(18,2) | >= 0                 |              |

**Rules**

- Unique index on (LoanId, Number).
- The sum of `PrincipalDue` across a loan's installments equals the loan's principal. The last installment absorbs rounding residue.
- No "paid" columns. Whether an installment is paid is worked out by comparing repayments to the schedule.

## LoanRepayment

One payment received against a loan.

| Field           | Type          | Constraints                          | Notes              |
| --------------- | ------------- | ------------------------------------ | ------------------ |
| Id              | int           | PK                                   |                    |
| LoanId          | int           | FK to Loan, Restrict                 |                    |
| Amount          | decimal(18,2) | > 0                                  |                    |
| PrincipalAmount | decimal(18,2) | >= 0                                 |                    |
| InterestAmount  | decimal(18,2) | >= 0                                 |                    |
| PaidOn          | DateOnly      |                                      |                    |
| JournalEntryId  | int           | FK to JournalEntry, Restrict, unique | The ledger posting |

**Rules**

- `PrincipalAmount + InterestAmount = Amount`.
- Posting: debit Cash, credit the loan's receivable account (principal), credit Interest Income (interest).
- Reversing a repayment reverses its journal entry. Keep the repayment row and mark it reversed rather than deleting it.

## SuspenseItem

Money received but not yet allocated to a loan or savings account.

| Field             | Type           | Constraints                  | Notes                             |
| ----------------- | -------------- | ---------------------------- | --------------------------------- |
| Id                | int            | PK                           |                                   |
| Amount            | decimal(18,2)  | > 0                          |                                   |
| ReceivedOn        | DateOnly       |                              |                                   |
| ExternalReference | string(100)?   | Unique where not null        | e.g. an M-Pesa transaction code   |
| PayerNote         | string(300)?   |                              | What is known about the payer     |
| Status            | SuspenseStatus |                              |                                   |
| ReceiptEntryId    | int            | FK to JournalEntry, Restrict | Debit Cash, credit Suspense       |
| AllocationEntryId | int?           | FK to JournalEntry, Restrict | Debit Suspense, credit the target |

**Rules**

- A "Suspense / Unallocated Receipts" liability account is added to the chart of accounts.
- Its balance must equal the sum of unallocated items. That reconciliation is a good test.
- Unique `ExternalReference` prevents the same payment being received twice.

## New seeded accounts for Stage 2

| Code | Name                            | Type      |
| ---- | ------------------------------- | --------- |
| 2100 | Suspense / Unallocated Receipts | Liability |

Per-customer savings accounts and per-loan receivable accounts are created at runtime under the control accounts `2000 Customer Deposits` and `1200 Loan Receivable`.

## Stage 2 changes to Stage 1 models

- `EntrySource` gains the new values listed above.
- No new columns on `Account`, `JournalEntry` or `JournalLine`. This is the test that Stage 1 was designed correctly.

## What each Stage 2 operation posts

| Operation           | Debit                           | Credit                                                        | Entry source       |
| ------------------- | ------------------------------- | ------------------------------------------------------------- | ------------------ |
| Savings deposit     | Cash                            | Member's savings ledger account                               | Manual             |
| Savings withdrawal  | Member's savings ledger account | Cash                                                          | Manual             |
| Interest accrual    | Interest Expense                | Member's savings ledger account                               | InterestAccrual    |
| Loan disbursement   | Loan's receivable account       | Cash or savings ledger account                                | LoanDisbursement   |
| Loan repayment      | Cash                            | Receivable account (principal) and Interest Income (interest) | LoanRepayment      |
| Payment to suspense | Cash                            | Suspense                                                      | SuspenseReceipt    |
| Suspense allocation | Suspense                        | Target (e.g. loan receivable)                                 | SuspenseAllocation |

# Stage 3: Robustness (planned)

## BatchRun

One row per job per business date. It answers "did this job already run for this day?"

| Field          | Type           | Constraints | Notes                       |
| -------------- | -------------- | ----------- | --------------------------- |
| Id             | int            | PK          |                             |
| JobType        | string(50)     | Required    | e.g. "InterestAccrual"      |
| BusinessDate   | DateOnly       | Required    | The date the job processes  |
| Status         | BatchRunStatus |             | Running, Completed, Failed  |
| StartedAt      | DateTime       | UTC         |                             |
| CompletedAt    | DateTime?      | UTC         |                             |
| ProcessedCount | int            |             | How many items were handled |
| Error          | string(2000)?  |             | Last failure message        |

**Rules**

- **Unique** on (JobType, BusinessDate).
- Each item inside the job also posts with its own `IdempotencyKey` (e.g. `accrual:{savingsAccountId}:2026-09-30`), so a crashed run can be safely re-run and will skip accounts already processed.

## Rounding account

No new table. Add one seeded account:

| Code | Name                 | Type    |
| ---- | -------------------- | ------- |
| 5900 | Rounding Differences | Expense |

When a calculation produces a fractional residue, the residue is posted to this account so the entry still balances. A growing balance here is a sign of a calculation problem.

## Account hierarchy

No new table. The existing `Account.ParentAccountId` is used fully:

- Reports roll sub-accounts up into control accounts.
- The trial balance can show either leaf accounts or control totals.

## Optional: multi-branch

Only if you want it.

| Model / change   | Fields                            | Notes                                               |
| ---------------- | --------------------------------- | --------------------------------------------------- |
| Branch           | Id, Code (unique), Name, IsActive | New table                                           |
| Account.BranchId | int? FK to Branch                 | Branch-level accounts under shared control accounts |

Branch reporting is then a filter on `Account.BranchId` plus hierarchy rollups.

# Delete behavior summary (all stages)

Everything uses **Restrict**. Nothing cascades, because nothing in an accounting system should disappear silently. Closed or unwanted records are deactivated or marked with a status.
